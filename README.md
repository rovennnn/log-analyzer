# log-analyzer

An ops dashboard for triaging application logs: upload a JSON-lines log file,
get request volume, error rate, slowest endpoints, and top error messages —
plus a sortable/filterable raw log table for drilling into specifics.

Built as a portfolio piece to show a real backend service (FastAPI) alongside
a proper frontend (Next.js/TypeScript), rather than another Streamlit script.

## What it looks like

- **Dashboard** — a time-series chart of requests + errors with a draggable
  brush that re-filters the whole page (status breakdown, slowest endpoints,
  top errors) to whatever window you select. Drag a spike, see what caused it.
- **Raw logs** — a dense, sortable, filterable table of every parsed event,
  for when you need to actually read the log lines.
- **Upload** — drop a `.jsonl` file, or click "try: ecommerce-api-36h.jsonl"
  to load the bundled sample data with zero setup.

## Tech stack

- **Backend**: FastAPI, SQLAlchemy, SQLite
- **Frontend**: Next.js 15 (App Router), TypeScript, Tailwind CSS, Recharts

## Log format

The parser expects **JSON-lines** — one JSON object per line — rather than a
text/regex format like Apache's Combined Log Format. This was a deliberate
choice: JSON-lines parses with `json.loads` + schema validation instead of a
hand-rolled regex, so one malformed line degrades gracefully (skipped and
counted) instead of derailing the whole upload or requiring a fragile pattern.
It also means every field the dashboard needs — log level, duration, status —
is native to the format rather than inferred.

Example line:

```json
{"timestamp": "2026-07-14T08:23:11.482Z", "level": "info", "service": "checkout-api", "method": "GET", "path": "/api/cart/1234", "status": 200, "duration_ms": 42, "ip": "10.0.4.22", "request_id": "a1b2c3", "message": "request completed"}
```

Required fields: `timestamp`, `level`, `method`, `path`, `status`,
`duration_ms`, `message`. Optional: `service`, `request_id`, `ip`.
`level` accepts common aliases (`warning`→`warn`, `crit`/`critical`→`fatal`,
`err`→`error`) and defaults to `info` if missing or unrecognized.

## Local setup

### Backend

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env             # adjust CORS_ORIGINS if needed
uvicorn app.main:app --reload --port 8000
```

The API is now at `http://localhost:8000` (interactive docs at `/docs`).
SQLite data lives in `backend/log_analyzer.db`, created automatically on
first run.

### Frontend

```bash
cd frontend
npm install
cp .env.local.example .env.local   # points at localhost:8000 by default
npm run dev
```

Open `http://localhost:3000`, go to **Upload**, and either drop a log file
or click one of the "try: ..." buttons to load the bundled sample data.

## Sample data

`sample-logs/` contains two files generated by
`sample-logs/generate_samples.py` — entirely synthetic (seeded random
generation, no real traffic/users/IPs), simulating a small e-commerce API
with a couple of injected incidents (a payment-gateway timeout spike) so the
dashboard has something interesting to show. Regenerate or resize them with:

```bash
cd sample-logs
python3 generate_samples.py
```

The frontend serves copies of these from `frontend/public/sample-logs/` so
the "try: ..." buttons on the Upload page can load them directly in-browser —
if you regenerate them, copy the new files there too.

## API endpoints

| Method | Path                 | Purpose                                      |
|--------|----------------------|-----------------------------------------------|
| POST   | `/api/upload`        | Upload + parse a `.jsonl` file                |
| GET    | `/api/files`         | List uploaded datasets                        |
| DELETE | `/api/files/{id}`    | Remove a dataset                              |
| GET    | `/api/analysis`      | Aggregated dashboard data (filterable)        |
| GET    | `/api/logs`          | Paginated/sortable/filterable raw log events  |

`/api/analysis` and `/api/logs` both accept `file_id` (required), and
optional `start`, `end` (ISO timestamps), `level`, `status_class`
(`2xx`/`3xx`/`4xx`/`5xx`). `/api/logs` additionally accepts `search`,
`sort_by`, `sort_dir`, `page`, `page_size`.

## Design notes

Dark-mode-first, monospace-forward — this is data meant to be scanned for
hours, not a marketing page. IBM Plex Mono handles all data-dense areas
(timestamps, tables, raw log lines); IBM Plex Sans (same type superfamily)
handles UI chrome only, so the two registers read as one designed system
rather than a mismatched pair. Color is two neutrals (near-black surfaces,
cool-gray text) plus one accent (`#F0483E`), reserved specifically for 5xx /
error-level anomalies — not decoration. Status codes and log levels get a
small, deliberate semantic ramp (muted sage for 2xx, steel-blue for 3xx,
amber for 4xx/warn, the accent red for 5xx/error/fatal) instead of default
chart-library colors. There's no motion beyond what's functional, and no
donut charts — request volume and error rate are a real labeled time-series,
because that's what you'd actually want mid-incident.

## Deploying

### Backend → Render or Railway

Both platforms build straight from `backend/` with a standard Python buildpack.

1. Point the service root at `backend/`.
2. Build command: `pip install -r requirements.txt`
3. Start command: `uvicorn app.main:app --host 0.0.0.0 --port $PORT`
4. Set the `CORS_ORIGINS` env var to your deployed frontend's URL (e.g.
   `https://your-app.vercel.app`).
5. SQLite writes to local disk — fine for a demo, but note that most
   free/ephemeral hosting tiers wipe local disk on redeploy or restart. For
   anything longer-lived, mount a persistent volume and point
   `LOG_ANALYZER_DB_PATH` at it, or swap in Postgres.

### Frontend → Vercel

1. Import the repo, set the root directory to `frontend/`.
2. Set the env var `NEXT_PUBLIC_API_URL` to your deployed backend's URL.
3. Deploy — Vercel auto-detects Next.js, no extra config needed.

## A note on dependency audits

`npm audit` will flag a few high-severity advisories inherited from Next.js's
own internal dependencies (`sharp` and a bundled `postcss`), both related to
the built-in `next/image` optimizer. This app doesn't use `next/image`
anywhere, so that attack surface isn't exercised, but keep dependencies
current and re-run `npm audit` before any real production deployment.
